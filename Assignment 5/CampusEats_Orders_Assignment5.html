Required Answers to Assignment Questions

1. For three of your endpoints, give the method, the success status, and the single response header that matters most — and why.
• POST /orders: 201 Created; Location: /orders/{orderId} matters most because the client cannot predict the generated order ID; Location provides the canonical resource URI to inspect or track.
• GET /orders/{orderId}: 200 OK; ETag matters most because it cryptographically fingerprints the representation, powering 304 conditional caching and 412 concurrency protection.
• DELETE /orders/{orderId}: 204 No Content; Cache-Control: no-store matters most because intermediate caches must immediately invalidate any stored copies and never serve stale cached deleted items.

2. Which of your endpoints are safe, and which are idempotent? Which one is neither, and how did you make it retry-safe?
Safe endpoints: GET /orders, GET /orders/{id}, OPTIONS. Idempotent endpoints: GET, OPTIONS, PATCH /orders/{id}, DELETE /orders/{id}. Neither safe nor idempotent: POST /orders and POST /orders/{id}/cancellation. POST /orders was made retry-safe via a mandatory Idempotency-Key header; repeated submissions return the cached original 201 response and Location without duplicate payment processing or food preparation.

3. Show one ETag from your service, the request that returns 304, and the write that returns 412. What does each save or prevent?
Example ETag: "0aa5da47aa253af6".
• GET /orders/ord-f8a326caa1a1 with If-None-Match: "0aa5da47aa253af6" returns 304 Not Modified. Saves: Eliminates redundant payload transmission, network latency, and client JSON parsing.
• PATCH /orders/ord-f8a326caa1a1 with If-Match: "stale-etag-99999" returns 412 Precondition Failed. Prevents: Prevents the Lost Update problem where concurrent edits overwrite newer modifications.

4. You return 422 for one case and 400 for another. Give the exact request that triggers each, and explain the difference.
• 400 Bad Request: POST /orders with {"customerId":"stu-102"} (missing required fields items and deliveryAddress).
• 422 Unprocessable Content: POST /orders/{id}/cancellation on an already cancelled or delivered order.
Difference: 400 signifies a syntactic/structural defect (malformed payload or missing required schema fields). 422 signifies a semantic/domain refusal (the JSON structure is valid, but business logic rejects the state transition in the entity's current state).

5. A browser page on another origin calls your API and is blocked — yet your server logs show a 200. Who blocked it, and which response header fixes it?
The client browser blocked it under the Same-Origin Policy (SOP). The server received the request, processed it, and returned 200, but because the response omitted cross-origin permissions, the browser prevented client-side JavaScript from reading the data. The Access-Control-Allow-Origin: * header (alongside OPTIONS preflight headers) fixes it.

6. Name one response where you set Cache-Control to allow caching and one where you must use no-store. Why each?
• Allow caching: GET /orders/{id} sets Cache-Control: private, max-age=60 because individual order details rarely change second-to-second; private caching allows the student's browser to reuse it while preventing public proxy caching.
• Must use no-store: POST /orders and PATCH /orders/{id} set Cache-Control: no-store because mutations and financial transactions must never be replayed from cache.

7. Your search endpoint is a GET. When would POST be the right choice instead, and what do you give up by switching?
POST is appropriate when query criteria become excessively large (e.g. hundreds of item IDs or complex nested filter trees exceeding URL length limits) or contain sensitive data that should not leak into browser history or URL logs. Switching to POST gives up automatic HTTP cacheability, browser back/forward navigation, URL bookmarkability, and link shareability.

8. Location appears on a 201 and on a 3xx. What does it point to in each case?
On 201 Created, Location points to the persistent URI of the newly created resource. On 3xx Redirection, Location points to the target URI where the client should re-dispatch its request next.
