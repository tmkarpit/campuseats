Part A — resource model

SOAP-style starting operations

placeOrder(customerId, items, deliveryAddress), getOrder(orderId), listOrders(status), and cancelOrder(orderId, reason).

Hard mapping choice

cancelOrder looks imperative. It is represented as creation of the durable cancellation sub-resource, /orders/{orderId}/cancellation, which has a request, state, and asynchronous processing. /cancelOrder was rejected as an RPC URL; DELETE /orders/{orderId} was rejected because the order must remain auditable and cancellation is not deletion.

Part B and C — contract and implementation

openapi.yaml is OpenAPI 3.0.3 and declares reusable request, response, and Problem schemas. Every operation has inputs and at least two responses. The preflight validator completed with zero structural errors.

$ python3 validate_openapi.py openapi.yaml
OpenAPI document parsed successfully.
Structural checks completed: 0 errors.

The service is dependency-free WSGI Python. Stored Order records include an internal UUID and payment reference, while as_json() omits both. validate() checks a request before accessing its fields. All failures use problem(type, title, status, detail).

POST /orders requires Idempotency-Key. The store atomically maps the key to one order; a repeat returns the original 201 result and Location header without another payment call.

Part D — resilient payment call

The payment address is read from PAYMENTS_URL, never hard-coded. A payment POST has a 2-second timeout, up to three tries, exponential backoff and jitter. Only connection/timeout and server-side transient errors can be retried; any 4xx stops immediately. The idempotency key goes on every payment request.

If Payments is absent or unreachable, the order remains PAYMENT_PENDING. This is safer than marking it paid or confirmed: it preserves the order and prevents delivery from treating an uncharged order as complete.

Comparison with SOAP / UDDI

1. The actual Assignment 3 TrustPay WSDL has 115 lines; openapi.yaml has 125, a difference of 10. OpenAPI describes resource paths, HTTP codes, JSON representations and reusable errors. The WSDL's SOAP binding and SOAPAction are unnecessary: HTTP methods/media types and the OpenAPI server URL supply those roles.

2. The actual SOAP fault contains <faultcode>soap:Client</faultcode>, Payment declined, and partner code CARD_DECLINED. REST returns 422 Unprocessable Content with {"type":"about:blank","title":"Payment declined","status":422,"detail":"Payment was declined. Please use another payment method."}. An error wrapped in 200 makes caches, gateways, monitoring and retry logic misread failure as success.

3. In Assignment 3, TrustPay was published in the partner catalogue; checkout found the active gateway record and WSDL pointer; then a generated client bound to the recorded endpoint. Here, publish is the OpenAPI file, find is deployment configuration through PAYMENTS_URL, and bind is a generic HTTP client using the documented method, path and JSON media type.

4. validate() now enforces request shape. Without it, a missing items field could become a server error or invalid order instead of a 400 response.

5. SOAP remains sensible for the actual TrustPay payment edge because it needs a strict message contract, message-level credentials and predictable faults—the purchased guarantee is an authenticated, integrity-protected, stable enterprise contract.
